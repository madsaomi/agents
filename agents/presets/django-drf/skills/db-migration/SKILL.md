# 🗄️ Безопасные миграции (Django)

## Железное правило
Миграция должна быть **безопасна на живой таблице**: применение не теряет данные и не блокирует таблицу надолго.

## Рецепты безопасных изменений

### Добавить поле
```python
# Фаза 1: добавить с default (НЕ nullable без нужды)
models.CharField(max_length=100, default="", blank=True)
# Фаза 2 (отдельная миграция): заполнить существующие строки RunPython батчами
# Фаза 3: переключить форму/код на новое поле
```

### Переименовать поле — НЕ через RenameField на проде
1. Новое поле `new_name` (миграция «add»);
2. backfill `new_name = old_name`;
3. dual-write в коде;
4. переключение чтения;
5. удаление `old_name` (отдельная миграция, позже).

### Удалить поле/модель
Сначала перестать читать/писать в коде (релиз), удалить — следующим релизом. `RemoveField` сразу = потеря данных.

### Большие таблицы
- `CREATE INDEX CONCURRENTLY` через `RunSQL` (или `AddIndexConcurrently`), не `CREATE INDEX`;
- backfill через `.iterator(chunk)` c `bulk_update`, в фоновой задаче;
- `AlterField` с сужением — только после очистки данных.

## Чек-лист перед применением
- [ ] Миграция протестирована на копии прод-данных, не только на пустой БД.
- [ ] `python manage.py makemigrations --check` — нет забытых миграций.
- [ ] Есть `down` или обоснование его отсутствия.
- [ ] Простой оценен: сколько строк, какая блокировка, сколько займёт.
- [ ] Ревью субагентом `django-migration-reviewer` для рискованных изменений.
